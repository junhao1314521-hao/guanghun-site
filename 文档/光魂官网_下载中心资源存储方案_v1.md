# 光魂官网 · 下载中心资源存储方案 v1

> 目标：把「素材库（文件）」和「下载中心（业务记录）」的边界定清楚，保证文件可复用、链接不失效、删除不误伤、可备份、可迁移。
> 依据：2026-11-22 对测试机数据与代码的实际核对，不是推测。

---

## 一、现状核对

### 1.1 测试机数据（2026-11-22）

| 项 | 数值 |
|---|---|
| 下载资料总数 | 53 条 |
| 其中文件在 `/uploads/` 且已登记素材库 | 42 条 |
| 其中没有文件（显示「待更新」） | 11 条 |
| 外链下载 | 0 条（测试机当前） |
| 素材库记录总数 | 71 条 |
| 上传目录体积 | 约 679 MB |
| 下载引用文件与 `upload_meta` 对应 | 42/42 全部对应 |
| 下载引用文件与磁盘对应 | 42/42 全部存在 |

结论：**测试机上，凡是有文件的下载资料，文件都在素材库里，且能对应到磁盘**；11 条是业务上还没上传文件。

### 1.2 代码现状

- 上传：`POST /api/admin/uploads` → 文件落 `data/uploads/` → 写 `upload_meta`。
- 素材库页面：`/admin/assets` 读取 `upload_meta`，与上传接口是同一份数据。
- 下载资料：`downloads` 集合的 `fileUrl` 是普通文件字段，上传时走同一套接口，所以默认进素材库；也允许直接填外链。
- 删除素材：软删除进回收站，磁盘文件保留；有 `/uploads/:id/references` 可查引用。
- 每日备份：`deploy/backup-db.mjs` **只备份 SQLite，不备份 `data/uploads/`**。

### 1.3 现有问题

1. **素材库没有区分用途**：图片、视频、3D 模型、固件、说明书混在一张 `upload_meta` 表里，只能按 MIME/分类粗分。
2. **删除没有强制引用保护**：素材被下载资料引用时仍可删除，下载链接会断。
3. **大小 / 校验值可能不一致**：下载记录里手填的 `size`、`sha256` 与真实文件可能对不上；本地上传文件虽然服务端会算 SHA-256，但没有作为唯一来源。
4. **版本覆盖风险**：`/uploads/:id/replace` 是原地替换同一 URL。图片可以，固件/驱动不行——用户可能缓存旧包，或需要回滚旧版本。
5. **外链没有约束**：可以手填任意 URL，没有格式校验、没有可用性检查。
6. **上传部分没有大文件保护**：没有分片/断点续传；2C2G 服务器上大文件上传与下载都走 Express。
7. **备份缺口**：数据库备份了，679 MB 的上传文件没有每日备份；一旦磁盘故障，下载中心与产品图一起丢。
8. **重复文件**：同一固件重复上传会占多份磁盘，没有按内容哈希去重。

## 二、总体约定（建议拍板）

### 2.1 两条主线，职责分开

| 层 | 负责 | 不负责 |
|---|---|---|
| **素材库（Asset）** | 二进制文件、原名、类型、大小、SHA-256、存储位置、可见性、引用计数 | 业务语义（哪个产品、哪个版本、是否最新） |
| **下载中心（Download Item）** | 资料名称、类型、适用型号、版本号、发布日期、是否最新、更新说明、引用哪个 Asset | 文件本身 |

**一句话：文件只存一份，下载记录只存「引用 + 业务信息」。**

### 2.2 只保留站内文件，不提供任意外链

每条可下载的下载资料必须有 `assetId`，`fileUrl / size / sha256` 都由 Asset 派生；没有文件时显示「待更新」。后台不再提供「手动填外链」的入口。

**行业做法（核对结论）**

- Microsoft / Google / NVIDIA / Apple 等大厂：下载文件放在**自家 CDN / 对象存储域名**（如 download.microsoft.com、dl.google.com、international.download.nvidia.com）。技术上跨域，但仍由公司自己控制、可校验、可统计，不属于「随手填一个第三方链接」。
- 开源项目：使用 GitHub Releases 等官方代码托管，属于「官方指定的唯一来源」，不是运营随手粘贴的网盘链接。
- 小团队 / 个人：会用百度网盘、蓝奏云、Google Drive 等第三方网盘，但这类链接有广告、限速、失效、无法校验文件完整性，不适合作为品牌官网的正式下载渠道。
- **结论**：品牌官网的通行做法是「文件由自己托管（本站或自家 CDN）」，不是「允许运营填任意外链」。我们已经有素材库，因此不保留任意外链入口。

**为什么不做任意外链**

1. **会失效**：第三方网盘 / 临时域名随时可能删除、限速、改规则，官网下载链接不可控。
2. **无法校验**：拿不到可信的 size / SHA-256，用户下载到篡改包也无法发现。
3. **无法统计与审计**：下载量、版本分布、异常来源都拿不到；出问题无法追责。
4. **无法备份**：外链文件不在我们的备份里，磁盘故障或迁移时无法保证可恢复。
5. **品牌与安全**：用户对「官网下载」有信任预期，跳到第三方网盘会降低信任，也增加钓鱼 / 恶意包风险。
6. **引用与删除**：外链不受素材库引用统计和删除保护约束，容易留下死链。

**未来如果上 CDN / 对象存储**

不是「开放外链」，而是新增一个由我们控制的 `storage driver`（local / OSS / CDN）：Asset 仍由素材库管理，`fileUrl` 由驱动生成；运营仍然只选素材，不手填 URL。

### 2.3 URL 稳定性

- 已存在的 `/uploads/<文件名>` **不重命名、不迁移**，避免历史链接、搜索引擎、用户收藏失效。
- 新上传文件继续使用「时间戳-随机串-原名」命名；真正的唯一标识是 `assetId`，不是文件名。
- 下载资料更新版本时：**新增一个 Asset + 新增一条下载记录**，旧版本记录保留并标记「旧版」。不要用 `replace` 覆盖固件文件。

### 2.4 公开与私有

- 当前所有 `/uploads/` 文件公开可访问，符合现状。
- 预留 `visibility: public | private`。私有文件（如仅保修用户可下）后续走签名 URL，不改变现有公开文件行为。

## 三、数据模型

### 3.1 素材库 Asset（在现有 `upload_meta` 上扩展）

| 字段 | 说明 |
|---|---|
| `id` | 现有：文件名。保留兼容；新增 `assetId`（稳定 ID，可用文件名） |
| `originalName` | 上传时的原始文件名 |
| `storageKey` | 实际存储相对路径（当前 = 文件名） |
| `mime` / `ext` | 服务端识别，不信任前端 |
| `sizeBytes` | 服务端统计，唯一来源 |
| `sha256` | 服务端流式计算，唯一来源 |
| `kind` | `image / video / model3d / document / firmware / installer / archive / other` |
| `usage` | `product / download / brand / page / other`（可多值或主用途） |
| `visibility` | `public / private`，默认 public |
| `status` | `active / archived / deleted` |
| `createdBy` / `createdAt` / `updatedAt` | 审计 |
| `refCount` | 引用数（可由查询派生，不必落库） |

> `kind` 与 `usage` 是这次最需要的两个字段：没有它们，素材库无法按「固件」筛选，也无法在删除时提示「被 3 条下载资料引用」。

### 3.2 下载资料 Download Item（`downloads` 集合扩展）

| 字段 | 说明 |
|---|---|
| `id` / `name` / `type` | 现有 |
| `assetId` | 内部文件引用；新增 |
| `fileUrl` | 兼容字段；由 Asset 派生，不手填 |
| `version` | 版本号（文本） |
| `releasedAt` | 发布日期 |
| `os` / `models` | 现有 |
| `isLatest` | 是否最新版本；同 `type + models` 下最多一条 true |
| `releaseNotes` | 更新说明（可选） |
| `size` / `sha256` / `checksumType` | **只读派生**：全部取自 Asset，不手填 |
| `status` | `active / hidden`（是否前台可见） |

## 四、上传与引用流程

### 4.1 上传（内部文件）

1. 前端选择文件 → 按 `kind` 校验扩展名 / MIME / 大小：
   - 图片 ≤ 10 MB
   - 视频 ≤ 200 MB
   - 文档（PDF/Office/ZIP）≤ 50 MB
   - 固件 `.bin` ≤ 100 MB
   - 安装包 ≤ 300 MB
   - 3D `.glb` ≤ 30 MB
2. 服务端流式写入临时文件，同时计算 SHA-256，不整文件读内存。
3. 校验通过后移动到 `data/uploads/`，写 `upload_meta`（含 kind/usage/size/sha256）。
4. 返回 `{ assetId, fileUrl, sizeBytes, sha256 }`。
5. 可选：按 SHA-256 去重，命中已有 Asset 时直接复用（先做提示，不自动删除旧文件）。

### 4.2 下载资料保存

- 选择「素材库文件」→ 写 `assetId`，其余 `fileUrl/size/sha256` 由服务端派生。
- 没有文件 → 允许保存为「待更新」，前台不显示下载按钮。
- 不提供手填 URL 的入口。

### 4.3 删除与替换

- 删除 Asset 前检查引用：
  - 被产品 / 下载 / 页面引用 → **阻止删除**，提示引用位置；
  - 未被引用 → 软删除进回收站，磁盘文件保留，定期清理。
- 图片替换：可继续使用 `/uploads/:id/replace`（URL 不变）。
- 固件 / 驱动 / 说明书：**禁止原地替换**；走「发布新版本」：
  - 新 Asset；
  - 新下载记录（`version` 递增，`isLatest=true`）；
  - 旧记录 `isLatest=false`，仍可下载。

## 五、交付与备份

### 5.1 下载交付

- 短期：继续由 Express 提供 `/uploads`，但给下载资料加：
  - `Content-Disposition: attachment`（PDF 在线阅读除外）；
  - `Cache-Control`：带哈希/时间戳的文件用长缓存；
  - `Accept-Ranges: bytes`，支持大文件断点续传。
- 中期：Nginx 直接 `alias /opt/website/data/uploads/`，应用只做鉴权与跳转，避免 Node 扛大文件。
- 后期：如需 CDN/OSS，抽象 `storage driver`（local / oss），Asset 存 `storageKey`，下载接口返回可用 URL。

### 5.2 备份（必须补）

- 现有：每日 SQLite 快照（7 天 + 4 周）。
- 新增：每日增量备份 `data/uploads/`（rsync 到同机 backup 目录或异地/NAS），每周全量保留 4 份。
- 恢复演练：从「SQLite + uploads」恢复后，随机抽 5 条下载资料验证可下载、SHA-256 一致。
- `upload_meta` 与文件必须同一时间点备份，避免「有记录没文件 / 有文件没记录」。

## 六、安全

- 服务端按扩展名 + MIME 双重校验；拒绝路径穿越、双扩展名伪装。
- 安装包 / 可执行文件允许上传，但前台只提供下载，不内嵌预览。
- 可选：ClamAV 病毒扫描（大文件异步扫描，扫描中标记 `pending`）。
- 下载接口限流与审计；后续私有下载用短时签名 URL。
- 素材库删除、替换进入操作日志（已有 audit 机制）。

## 八、验收标准

- 每条有文件的下载资料都有 `assetId`；`fileUrl` 由 Asset 派生，不手填。
- 下载资料的 `size` / `sha256` 与磁盘文件一致（脚本抽检 100%）。
- 删除被引用的 Asset 会被阻止，并给出引用位置。
- 素材库能按「固件 / 驱动 / 说明书 / 图片 / 视频 / 3D」筛选。
- 发布新固件后，旧版本仍可下载，最新版标记正确。
- 数据库 + uploads 能在新机器完整恢复，抽检下载链接 200 且 SHA-256 一致。
- 下载表单不存在手填 URL 入口；所有可下载资料都有 `assetId`。

## 九、已确认与待确认

**已确认**

- 不做任意外链：下载文件统一由素材库托管；未来上 CDN/OSS 也走受控的 storage driver，不开放运营手填 URL。
- 现有 2 条 `dl.guanghun.example` 本地种子外链是占位数据，不作为正式来源；测试机当前没有外链记录，无需迁移。

**待确认**

1. **固件是否保留旧版本？** 建议保留，且禁止原地覆盖。
2. **是否现在就把上传目录迁到 Nginx/OSS？** 建议先补备份与元数据，等文件量和带宽上来再迁。
